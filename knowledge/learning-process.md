# 需求學習與維護

1. 每次任務開始，檢查實際可取得的當次訊息、已匯入需求及倉庫變更。沒有跨對話存取權時記錄限制，不能假設已同步。
2. 比對 requirements.json 的 ID、範圍與驗收條件；既有要求更新同一 ID，新要求建立新 ID。來源只記錄去識別概述，私人對話全文不入庫。
3. 將觀察、待確認推論、已確認規則分開。政策衝突交主管處理；無法以證據解決的部分阻擋相關計算。
4. 修改最小相關規則/程式；加入能重現該要求的合成測試。執行完整 unittest 及公開內容檢查。
5. 測試通過後提交，摘要列明需求 ID、行為改變、驗證及限制。不得為了「自我優化」自行放寬資格規則或擴大外部權限。
6. 本專案所稱「自我訓練」是從已確認的新需求、修正與失敗案例學習：更新去識別 knowledge、routing、agent instructions、deterministic helpers 與 synthetic regression tests。不得把真實申請人姓名、學號、成績、原始 PDF/影像或 Drive 內容提交為公開訓練資料，也不得未經確認把單一案例擴張成通用資格政策。

GitHub Actions 的排程測試只驗證已提交程式，不能讀私人專案新對話。ChatGPT/Codex 長期排程若已建立，應讀取可見需求與 GitHub 狀態，先執行 regression/self-test，再判斷是否有可泛化改善；有具體變更才更新，沒有新資訊時不做無意義提交。定期檢查不構成持續讀取私人 Drive 申請資料的授權。

批次整理或本機補件時，先依 rules/batch-coverage.md 核對來源清單及逐頁覆蓋。
